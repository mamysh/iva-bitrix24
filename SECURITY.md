# Security Policy

## Supported versions

Исправления безопасности выпускаются для текущей стабильной линии и состояния ветки
`main`. Более старые линии не поддерживаются.

## Reporting a vulnerability

Используйте **Security → Report a vulnerability** в GitHub-репозитории. Private Vulnerability
Reporting позволяет обсудить проблему без публичного issue.

В сообщении укажите затронутую версию или commit, сценарий воспроизведения, ожидаемое влияние
и безопасный синтетический пример. Не присылайте действующий webhook, домен частного портала,
данные задач, полные ответы Bitrix24 или секреты других систем.

Обычные ошибки без влияния на безопасность можно публиковать в GitHub Issues.

## Secret exposure

Полный URL входящего webhook Bitrix24 является секретом. Если он попал в commit, issue, PR,
лог, artifact или чат, немедленно отзовите либо пересоздайте webhook. Удаление строки из
последующего commit не отменяет компрометацию и не очищает историю.

Ответы Bitrix24 считаются недоверенными. Плагин не возвращает `error_description`, принимает
только короткие error-коды заданного формата и заменяет остальные на `UPSTREAM_ERROR`.
Вложенные объекты пользователя и группы внутри задачи сокращаются до проверенного ID и
ограниченного имени; email, телефоны, адреса, аватар, профильные URL и неизвестные поля
отбрасываются. Отдельный ограниченный поиск сотрудников может вернуть email профиля только
при scope `user_basic` или `user`. Задачи и события
истории без корректного safe-integer ID пропускаются, неизвестное имя history event не
отражается наружу, а actor history не содержит login или отчество.
Connection check ограничен профилем и метаданными scope: skill запрещает дополнять его
выборкой задач, их количеством, названиями или сроками без отдельного запроса владельца.

Дополнительные read-tools используют отдельные scopes и фиксированный REST allowlist.
Capability-диагностика отражает только известные плагину права. Поиск сотрудников возвращает
ограниченный рабочий профиль и требует ID, строки имени либо конкретного подразделения.
Телефоны, адреса и фото не запрашиваются даже с `user_basic`; выдача и пагинация имеют
жёсткие лимиты. Task chat, его системные события, комментарии, checklist text и имена файлов
считаются недоверенным содержимым, даже когда используются для аналитики изменений задачи.
Download/view URL Bitrix24 не возвращаются модели и не логируются. Выбранный файл скачивается
только с исходного HTTPS-портала, поток ограничен 50 МиБ. Копия размещается с правами
`0600` в `vault/attachments/bitrix24-read/` и удаляется после успешной отправки или разбора;
при ошибке отправки сохраняется для повтора. Передача в Telegram идёт через отдельный плагин
`iva-file-delivery`. Содержимое документов, комментарии и имена файлов остаются недоверенными
данными. Связи задач читаются только на один уровень без рекурсивного обхода.

## Обновление из чата

Интерактивный серверный установщик может установить LibreOffice после отдельного ответа
владельца. Telegram-updater сообщает об отсутствии пакета и показывает команду для ручного
запуска по SSH, только если подтвердил путь установленной Ивы и наличие пакетов для
Ubuntu/Debian. Сам updater не запускает `sudo` или пакетный менеджер.

Сервис обновлений не принимает имя плагина, URL репозитория, ref или произвольную команду.
Он читает уже записанный Iva GitHub-источник только для `bitrix24-read`, создаёт предложение
на конкретный SHA и разрешает запуск лишь в течение 15 минут после успешного GitHub Actions.
Отображаемые версии читаются из установленного manifest и из manifest ровно на candidate SHA;
оба значения проходят строгую SemVer-проверку. Удалённый manifest ограничен по размеру,
запрашивается без редиректов и не меняет привязку подтверждения к полному SHA. Offer создаётся
только для более высокой SemVer: commit с той же версией и откат ref на старую версию не
создают обновляющее действие.
Skill запрашивает выбор через встроенный `ask_question`; Eve/Iva паркует ход и возвращает
нажатую Telegram-кнопку как структурированный ответ. Apply дополнительно требует одноразовый
token того же offer. Offer и job-файлы имеют режим `0600` и не содержат webhook или данные
задач.

Обновление выполняется штатным `iva plugin update` в отдельном transient systemd unit, после
чего запускается `iva doctor`. При провале диагностики worker пытается восстановить предыдущий
SHA того же источника. Экземпляр из локальной папки через чат не обновляется.

Tool восстанавливает только адрес локального user-systemd bus и запускает unit неблокирующе.
Worker вызывает точный `~/.local/bin/iva`, не доверяет `PATH` и не использует sudo. При ошибке
запрещён fallback через shell или дочерний процесс `iva.service`: пересборка может остановить
родительский cgroup раньше, чем такой процесс успеет вернуть сервис.

MCP-процесс не получает Telegram-токен или остальное окружение агента. Однако передача
token из structured button response в apply идёт через модель, поэтому это не
криптографическая авторизация. Риск ограничен ранее доверенным Git-источником этого плагина,
свежим SHA, зелёным CI и TTL offer. Данные задач, файлы и пересланные сообщения никогда не
считаются выбором кнопки.

## Действия с задачами (0.6.0)

Allowlist чтения остаётся отдельным от allowlist записи. Сервер записи принимает только
типизированную задачу или действие, фиксирует payload и перед записью проверяет владельца,
портал, права и снимок задачи. Делегирование ограничено правами Битрикс24, без локального фильтра подчинённости. Один pending-черновик на webhook-владельца;
другой prepare отменяет прежний. UUID не является доказательством нажатия кнопки: как и для
updater, native structured answer или точный ответ rich-кнопки передаётся apply через модель. При компрометации модели
этот workflow сам по себе не обеспечивает независимый human-approval gate.

State хранится в private PLUGIN_DATA с режимами 0700/0600. Активный черновик содержит рабочий
текст и выбранный относительный путь; после результата он удаляется. Квитанция содержит
только владельца/портал, действие, ID задачи, безопасный код результата и прогресс чек-листа.
Запись квитанции предшествует сетевому вызову; неизвестный результат никогда не повторяется
автоматически. Блокировка закрывает конкурентное выполнение; после аварии требует проверки
оператором. Каталог квитанций нельзя очищать с целью повторить запрос.

Загрузка читает только выбранный локальный файл внутри attachments, проверяет realpath,
тип, размер до 50 МиБ и SHA-256 перед выполнением; принимает Base64 только внутри процесса.
Не принимает chat ID или внешний URL от модели: чат определяется из текущей задачи.
Содержимое task/chat/file и тексты превью остаются недоверенными данными.

Предварительная версия 0.7.0-rc.2 фиксирует весь batch в одном черновике.
Общий preflight проверяет все пункты до первой записи, права и маршрут проверяются также
перед последующим действием. Частичный результат не повторяется и не считается откатом.
Квитанции содержат упорядоченный прогресс, ID отправленного файла/сообщения и безопасные коды,
без текстов сообщений или Base64. Update не допускает произвольные REST fields и не обходит
ограничение reassignment. При восстановлении attachments root плагин читает настройку vault
только из проверенной установки CLI; конфиг и остальные env values не выдаются модели.

Удаление ограничено выбранным файлом или сообщением текущего чата доступной задачи.
Сервер сам определяет chat ID; принадлежность сообщения и файла проверяется до превью
и перед записью. Удаление файла допускается для его отправителя и проверяется чтением
после ответа API: true может означать отсутствие изменений. Произвольный disk.file.delete
не разрешён. Стадии берутся из канбана текущего проекта, права перемещения повторно
проверяются перед записью. Все эти операции входят в общий подтверждаемый batch.

Approval labels also request account EMAIL only under user_basic or user, never broader
contact fields. Without returned email they keep an explicit name/ID fallback. Named checklist
roots and their child IDs are persisted before subsequent writes; old pending draft schemas
require a fresh preview after upgrade. Existing receipts are preserved.

RC6: rich-превью экранирует данные задач; только сервер добавляет кнопки. Rich apply требует
отдельный случайный ответ текущего offer, а не один draftId. Это связывает сообщение с
черновиком и предотвращает случайный выбор старой кнопки, но модель видит ожидаемый ответ:
независимого доказательства нажатия нет. Skill разрешает apply только после соответствующего
входящего сообщения владельца. Allowlist отправителя применяет существующий Telegram-poll
Ивы; plugin не получает Telegram credentials и не создаёт собственный callback endpoint.

RC7: дополнительные сведения о текущем/новом ответственном ограничены WORK_POSITION
и именами подразделений из UF_DEPARTMENT. department.get вызывается только при уже
выданном scope department; отсутствие/отказ optional lookup не расширяет права и не
блокирует разрешённую запись. Кэш названий живёт только в пределах одного prepare.


## Настройки плагина (предварительный выпуск 0.7.1-rc.1)

Меню плагина использует тот же model-mediated callback путь, что rich-подтверждение задач.
Сервер не удостоверяет независимо факт человеческого Telegram-нажатия. Skill принимает
только реальный ответ владельца в личном чате; при компрометации модели этот протокол не
является независимым human-approval gate. Подтверждение требует fresh offer, exact reply,
TTL10 минут, owner/portal identity и неизменной revision. Второе предложение заменяет первое;
после применения revision не позволяет повторить старый ответ. Навигация не меняет policy.

Детерминированные ограничения применяются в TaskWriter до prepare/apply и перед каждой
mutation. Read-only закрывает все записи на портал; upload/delete flags действуют на весь
составной запрос. Общая filesystem lock сериализует task writes/settings commits. Смена
политики удаляет pending task preview до атомарного settings commit; schema5 связывает
новое превью с revision. Завершённые квитанции сохраняются, чтение их результата не является
новой mutation. Самостоятельное удаление settings возвращает исходные env defaults и потому
не является безопасным способом исправления повреждения.

Сокращение персональных данных применяется перед MCP-output (с повторным чтением актуальной
policy после запроса) и при составлении превью. Optional employee SELECT ограничен режимом;
не запрашиваются имена в ids, work position/departments в ids/names, EMAIL при выключенном
email. IDs и признаки ACTIVE сохраняются для адресации/проверки доступности. Profile и
некоторые методы Bitrix возвращают больше полей независимо от SELECT: лишние поля в модель
не передаются. Свободный текст, history values, файлы/их имена и прежняя память Ивы не
обезличиваются. Минимизация не гарантирует отсутствие любых персональных данных.

Private settings/offer файлы 0600, каталоги 0700, атомарная запись с fsync. Повреждённая policy
закрывает штатные read/write методы до запроса данных; без PLUGIN_DATA политика read-only/IDs.
Installer 0.7.1-rc.1 маркирует только новую конфигурацию restricted; legacy defaults при отсутствии
маркера/старом env описаны в SETUP. Изменение webhook secret и scope остаётся вне чата.
