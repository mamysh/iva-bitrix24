# Release process

## Проверки перед релизом

1. Обновить CHANGELOG и заявленную матрицу совместимости.
   Для каждого публикуемого RC также увеличить SemVer в `package.json` и `plugin/plugin.json`:
   updater показывает именно manifest-версии установленной и кандидатной сборки.
2. Выполнить `npm ci` и `npm run check` на чистом checkout. Distribution check обязан
   подтвердить одинаковую SemVer, Marketplace metadata и лимиты пакета Iva.
3. Выполнить `npm audit` и проверить лицензии зависимостей.
4. Убедиться, что `plugin/server.mjs`, `plugin/setup.mjs` и `plugin/update-worker.mjs`
   совпадают с результатом воспроизводимой сборки.
5. Проверить diff и достижимую git-историю на секреты, реальные URL и рабочие данные.
6. Проверить issues, PR, Actions logs и artifacts, относящиеся к релизу.
7. Провести установку, trust, connection check, disable и повторный enable на поддерживаемой
   версии Iva без сохранения ответов частного портала.
8. На тестовой Iva проверить chat update: check, точное подтверждение, background status,
   совпадение SHA и `iva doctor`; отдельным заведомо плохим кандидатом проверить rollback.
9. Убедиться, что README, About, topics, manifest, skill и документация описывают фактический
   контракт текущего bundle, а приватный план и локальная память не staged.
10. Ротировать любой временный webhook, использованный при ручной проверке.
11. Обновлять `docs/COMPATIBILITY.md` только для сочетаний, подтверждённых CI или отдельным
    живым smoke-test; один успешный запуск процесса не считается проверкой совместимости.

## Версионирование

Проект использует SemVer. До `1.0.0` несовместимые изменения допускаются только с явным
описанием в release notes. Стабильный релиз создаётся из проверенного commit ветки `main`:

```bash
git tag -a vX.Y.Z -m "iva-bitrix24 vX.Y.Z"
git push origin vX.Y.Z
```

Если у владельца настроена проверяемая signing key, аннотированный тег следует подписать
через `git tag -s`. Наличие подписи нельзя заявлять без успешного `git tag -v`.

Release notes должны описывать пользовательские изменения, требования к Iva, миграцию и
изменения разрешений. Не включайте в них данные ручного smoke-test.

Repository-level immutable releases включены 8 сентября 2026 года. GitHub применяет эту
настройку только к будущим releases, поэтому `v0.4.0`, опубликованный раньше включения, не
помечен immutable. Следующий release сначала создавать draft, прикладывать все нужные assets
и только затем публиковать: после публикации его tag и assets будут заблокированы GitHub.

Marketplace и installer этого репозитория отслеживают `stable`, чтобы штатный updater Iva
предлагал обычным пользователям только стабильные выпуски. Перед релизом проверить, что
ветка `stable` всё ещё указывает на предыдущий проверенный stable commit, а после публикации
перевести её fast-forward на новый stable tag. Проверить, что `.agents/plugins/marketplace.json`
предлагает `bitrix24-read`, указывает на `plugin/` этого GitHub-репозитория и совпадает с manifest.
Любое изменение содержимого `plugin/` обязано сопровождаться увеличением manifest-версии;
distribution check отклоняет изменение без version bump. Документационные commits с той же
версией updater пользователю не предлагает.

Checksum, опубликованный рядом с архивом на том же GitHub Release, выявляет повреждение
скачивания, но сам по себе не подтверждает автора. Не заявлять криптографическую подпись,
пока релизный ключ не настроен и подпись не проверяется отдельным доверенным путём.
