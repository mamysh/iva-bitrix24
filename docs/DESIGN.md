# Design principles

`iva-bitrix24` даёт Iva ограниченное чтение задач одного Bitrix24-портала без изменения ядра
Iva и без общего backend.

## Цели

- устанавливаться и удаляться штатными командами Iva;
- обеспечивать read-only режим техническим allowlist, а не только инструкцией модели;
- хранить webhook отдельно от репозитория и основного окружения агента;
- возвращать ограниченные нормализованные ответы;
- переживать обновление Iva без патчей её исходного дерева;
- использовать только синтетические данные в тестах и документации.

## Не входит в текущую версию

- создание, изменение, завершение или удаление задач;
- произвольный REST-вызов по имени метода;
- OAuth и установка одного приложения в несколько порталов;
- входящие события и публичный backend;
- чтение комментариев, файлов, сотрудников или групп без отдельного scope-review.

## Архитектура

```text
Iva
  -> generated MCP connection
    -> local Iva MCP proxy
      -> plugin stdio MCP server
        -> allowlisted HTTPS POST
          -> Bitrix24 incoming webhook
```

Webhook доступен только процессу плагина. MCP-контракт принимает типизированные аргументы и
не принимает URL или имя REST-метода. Сервер запрещает редиректы, ограничивает размер ответа,
применяет конечный retry только к временным ошибкам и возвращает безопасные коды ошибок.

## Модель доступа

Защита состоит из независимых слоёв:

1. отдельный пользователь Bitrix24 с минимальными правами;
2. webhook только со scope `task`;
3. закрытый allowlist REST-методов;
4. отдельные MCP-инструменты со строгими схемами;
5. нормализация и ограничение возвращаемых полей.

Публичный контракт ограничен перечисленными в README инструментами. Любое изменение
контракта требует отдельного review разрешений и приватности, обновления allowlist и
отрицательных тестов.

## Совместимость

Текущая реализация использует стабильные методы `tasks.task.*`. Публичные имена MCP-tools и
их read-only семантика составляют совместимый контракт плагина.

Подробные решения и их последствия зафиксированы в [ADR](adr/).
