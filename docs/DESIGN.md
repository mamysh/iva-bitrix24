# Design principles

`iva-bitrix24` даёт Iva ограниченное чтение задач одного Bitrix24-портала без изменения ядра
Iva и без общего backend.

## Цели

- устанавливаться и удаляться штатными командами Iva;
- обеспечивать read-only режим техническим allowlist, а не только инструкцией модели;
- хранить webhook отдельно от репозитория и основного окружения агента;
- возвращать ограниченные нормализованные ответы;
- переживать обновление Iva без патчей её исходного дерева;
- проверять и обновлять этот уже установленный плагин из чата без произвольного shell-доступа;
- использовать только синтетические данные в тестах и документации.

## Не входит в текущую версию

- создание, изменение, завершение или удаление задач;
- произвольный REST-вызов по имени метода;
- OAuth и установка одного приложения в несколько порталов;
- входящие события и публичный backend;
- чтение комментариев, файлов, сотрудников или групп без отдельного scope-review.

## Архитектура

```text
Iva
  -> generated MCP connection
    -> local Iva MCP proxy
      -> plugin stdio MCP server
        -> allowlisted HTTPS POST
          -> Bitrix24 incoming webhook

owner confirmation in Telegram
  -> bounded MCP update tool
    -> transient user-systemd worker
      -> iva plugin update bitrix24-read
        -> SHA verification -> iva doctor -> success or previous-SHA rollback
```

Webhook доступен только процессу плагина. MCP-контракт принимает типизированные аргументы и
не принимает URL или имя REST-метода. Сервер запрещает редиректы, ограничивает размер ответа,
применяет конечный retry только к временным ошибкам и возвращает безопасные коды ошибок.

## Модель доступа

Защита состоит из независимых слоёв:

1. отдельный пользователь Bitrix24 с минимальными правами;
2. webhook только со scope `task`;
3. закрытый allowlist REST-методов;
4. отдельные MCP-инструменты со строгими схемами;
5. нормализация и ограничение возвращаемых полей.

Задача нормализуется в стабильные типы: ID — ограниченные десятичные строки, статусы и
приоритеты — коды со стабильными именами, даты — только ISO 8601 с offset. Имена автора,
ответственного и группы извлекаются только из вложенных объектов той же задачи;
дополнительные `user`/`sonet` scopes не требуются. Повреждённые элементы страницы, включая
объекты без валидного ID, дают явный частичный результат, а повреждённая оболочка или
несовпадение ID одиночной задачи — безопасную ошибку. Режим просроченных использует
документированный Bitrix24-фильтр и сообщает точный `asOf`. Полный контракт описан в
[TASK_CONTRACT.md](TASK_CONTRACT.md).

Проверка подключения намеренно отделена от чтения рабочих данных: она вызывает только
`profile` и `tasks.task.getFields`. Skill не использует task list как дополнительный probe и
не показывает задачи без отдельного запроса владельца; ответ явно содержит
`taskContentChecked: false`.

Публичный контракт ограничен перечисленными в README инструментами. Любое изменение
контракта требует отдельного review разрешений и приватности, обновления allowlist и
отрицательных тестов.

## Совместимость

Текущая реализация использует методы `tasks.task.*` существующего REST API. Публичные имена
MCP-tools и их read-only семантика составляют совместимый контракт плагина. Проверенные версии
и явно неподдерживаемый REST 3.0 перечислены в [COMPATIBILITY.md](COMPATIBILITY.md).

Подробные решения и их последствия зафиксированы в [ADR](adr/).

## Контур обновлений

Check читает безопасные поля `source/ref/sha` текущей записи `bitrix24-read`, разрешает remote
SHA через `git ls-remote` и проверяет GitHub Actions. Он не меняет сервер. Apply принимает
только SHA и точную фразу из свежего локального offer; имя, URL, ref и CLI-аргументы в MCP-
схеме отсутствуют.

Worker запускается через `systemd-run --user --no-block` с явно восстановленным адресом
user-systemd bus, потому что MCP-процесс намеренно получает урезанное окружение. Перед первым
изменением worker оставляет 30-секундное окно для завершения и доставки ответа tool в
Telegram. Затем он
вызывает точный пользовательский `~/.local/bin/iva`, а не ищет CLI через `PATH`: так процесс
остаётся вне cgroup основной `iva.service` и переживает её штатную пересборку и рестарт.
Worker всегда берётся из текущего установленного snapshot. Поэтому изменение самого updater
можно подтвердить только следующим обновлением после установки исправленной версии.

Результат сохраняется в `PLUGIN_DATA/update-jobs/`; status возвращает только нормализованные
стадии и SHA и помечает старую job как `superseded`, если установленное состояние уже ушло
вперёд другим контролируемым путём. Job, не вышедшая из `queued` за две минуты, показывается
как `stalled`, а ошибка запуска worker нормализуется без вывода bus/path diagnostics.
Сборочный rollback обеспечивает Iva. Если переключение
состоялось, но `iva doctor` завершился ошибкой, worker переустанавливает прежний SHA того же
источника. После такого возврата источник остаётся pinned до отдельного решения владельца.
