# ADR0017: самостоятельное подтверждение кадровых заявок

Дата: 2026-11-04. Статус: реализовано локально в кандидате 1.0.0-rc.2;
выпуск, установка и живой Telegram-сценарий проверяются отдельно.

## Решение

Заменить обязательный Panels chat transport из ADR0014/0015 обычным rich-ответом
Ивы и маршрутом Telegram-poll tap. Приглашение, изменение профиля и увольнение
используют одну реализацию; настройки, задачи и updater сохраняют собственные пути.
Ядро Ивы, Telegram credentials и конфигурация внешнего роутера не меняются.

`present` проверяет сохранённое превью и до показа атомарно сохраняет случайный
96-bit token с draftId/version, identity, fingerprint, createdAt/expiresAt и state.
Возвращает rich markdown с `b24e:ok:<token>` / `b24e:no:<token>`, меньше 64 байт,
вне служебного пространства iva_. Повторный present возвращает тот же токен и срок.
Карточка живёт до 10 минут, не дольше 30-минутного черновика.

Навык распознаёт точную команду в первой строке текущего owner turn. Добавленная
мостом цитата карточки — данные, а не согласие. `bitrix24_employee_reply` принимает
только полную точную команду без цитаты. Токен из tool result, старого хода или
портала использовать как согласие нельзя; свободное «да» недостаточно.

Плагин проверяет подключение, версию, fingerprint, срок, настройки и состояние.
Подтверждение и queued сохраняются одним commit под общей policy lock. Отмена
закрывает draft, не пишет в портал. Повтор/неизвестный/просроченный токен получает
refused, без новой попытки. Изменение постороннего черновика не отзывает chat-offer.

После принятия MCP пробует выполнить существующий worker и вернуть контрольное
чтение. Собственная фоновая служба Bitrix продолжает queued после сбоя MCP.
Успех — только applied после read-back; ошибка наблюдения после commit не превращает
принятую заявку в разрешение повторить запись. Running после аварии даёт unknown.

## Граница доверия

Подтверждение проходит через модель. Плагин не получает независимой аттестации
физического клика и не отличает его от вручную введённой идентичной строки.
Ошибочное использование известного модели действующего токена не устраняется
валидацией токена. Это явное изменение границы из обязательного Panels маршрута,
согласованное владельцем. Права/scope, snapshot, блокировки, intent и запрет retry
unknown сохраняются. Доверенные процессы одного UID не изолированы друг от друга.

Обычный сценарий рассчитан на владельца личного Telegram-poll чата с tap и rich
replies. Поддержка групп/других транспортов не заявляется. Старые видимые кнопки
могут оставаться; от повторного эффекта защищает сохранённая квитанция.

## Совместимость и эксплуатация

Ни один обычный сценарий не вызывает API/сокет iva-panels. Старый provider API
и managed-служба Bitrix с именем panels сохранены для совместимости регистрации,
старых квитанций и восстановления очереди. Это служба самого Bitrix, её нельзя
отключать вместе с отдельным плагином iva-panels. Токены chat и legacy API не
взаимозаменяемы. Старые offers читаются без миграции; новые поля channel/fingerprint
не читаются строгой схемой RC1. Downgrade требует отдельной миграции с сохранением
истории и сверкой незавершённых/unknown действий, без удаления журнала.

Вывод iva-panels из входящего маршрута сообщений и его отключение — отдельная
операторская задача после проверки фактического маршрута. Локальная реализация
Bitrix не меняет ASSISTANT_HOST, поллер или системные drop-in.

## Проверки

Unit: отмена, применение один раз, restart/replay, конкуренция, expiry/correction,
смена policy, внешние изменения, unknown/no-retry и отказ межтранспортным токенам.
Собранный MCP: actual discovery/callTool, invite/cancel/update/dismiss/read-back и
настройки без процесса/сокета/каталога iva-panels, только искусственный портал.
Вся прежняя матрица задач, settings, updater и legacy provider остаётся обязательной.
Это не живая приёмка Telegram и не реальные кадровые операции.
