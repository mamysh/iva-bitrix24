# ADR 0016: увольнение как отдельная подтверждаемая кадровая операция

Дата: 2026-10-29. Статус: реализовано в 1.0.0-rc.1.

## Решение

Разговорный запрос на увольнение использует существующие candidates и employee_draft,
а не произвольный REST-вызов. Новое действие `dismiss` принимает только выбранный `userId`.
Прочие поля отклоняются. Неоднозначное удаление из отдела требует уточнения намерения.

Предварительное чтение получает актуальные ФИО, рабочую почту, должность, подразделения
и ACTIVE. Карточка показывает выбранный профиль, переход «Активен → Уволен» и последствия.
Транспорт Panels и фактическая кнопка подтверждения остаются общими; собственная очередь,
блокировка policy, fingerprint и проверка результата принадлежат Bitrix-плагину.

Worker отправляет только `user.update {ID, ACTIVE:"N"}`. Он требует тот же employees opt-in,
confirmed_write/work/email, scope user/department и реальные права портала. Уже неактивный
профиль и аккаунт из URL webhook не допускаются. Перед эффектом сверяются исходный профиль,
подразделения и revision настроек. Изменённый снимок требует нового превью.

Успех требует неактивного профиля в контрольном `user.get`. Уволенный пользователь может
вернуть UF_DEPARTMENT=[0]; нулевая запись нормализуется только для неактивного профиля,
для активного по-прежнему считается недопустимой. Ответ true сам по себе не успех.
Неизвестный исход сохраняется и не повторяется, включая restart и повтор кнопки.

## Границы

Увольнение не удаляет историю и не восстанавливает пользователя. Плагин не передаёт дела,
не меняет права, не обещает отзыв всех сессий и не управляет webhook других пользователей.
Действия с интеграциями остаются у администратора. Новые REST-методы не добавляются.
Процессы одного UID по-прежнему доверенные; атомарной транзакции с порталом нет.

Журнал с новым action не понимается предыдущими версиями. Downgrade требует явной миграции
с сохранением квитанций и сверкой unknown; удаление журнала ради повтора не допускается.

## Проверки

Синтетический портал покрывает полную цепочку подтверждения и контрольного чтения,
отмену/коррекцию, запрет self-dismissal, отказ прав, stale profile/settings, проигнорированное
обновление, потерю ответа и повторы после restart. Собранный MCP и реальный Unix socket
проверяются отдельно. Эти проверки не заменяют установку и ручной сценарий в Telegram.
