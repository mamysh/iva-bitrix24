# Установка и настройка

[← О плагине](../README.md) · [Вся помощь](README.md)

## 1. Подготовьте Bitrix24

1. Создайте отдельного пользователя интеграции либо выберите пользователя с минимально
   необходимым доступом к задачам.
2. Ограничьте доступ задачами, которые разрешено читать и изменять через Iva.
3. Откройте **Приложения → Ресурсы разработчика → Готовые сценарии → Другое → Входящий
   webhook** и на шаге **Права доступа** обязательно добавьте **Задачи** (scope `task`).
4. Для действий с задачами добавьте **Пользователи (минимальные)** (`user_brief`).
   Для дополнительных возможностей добавьте только нужные права:
   - **Чат и уведомления** (`im`) — обсуждение новой карточки и отправка файла в чат задачи;
   - **Рабочие группы социальной сети** (`sonet_group`) — проекты и группы;
   - **Пользователи (минимальные)** (`user_brief`) — имена, должности и подразделения;
   - **Пользователи (базовые)** (`user_basic`) — используйте вместо `user_brief`, только если
     Иве нужна рабочая почта рядом с именем сотрудника, в том числе в подтверждениях. Bitrix24 открывает этому scope и другие
     контакты, но плагин их не запрашивает и не возвращает;
   - **Структура компании** (`department`) — чтение подразделений; для смены ответственного не требуется;
   - **Диск** (`disk`) — метаданные и скачивание доступных файлов задач и чек-листов.
5. Не копируйте URL webhook в чат, issue, документ, командную строку или репозиторий.

Администраторские права не требуются и не рекомендуются: REST API видит задачи в пределах
прав пользователя, создавшего webhook. Scope и права пользователя проверяются отдельно:
Scope разрешает группе методов работать, но не даёт пользователю доступ к чужой задаче,
чату, файлу или проекту. Базовое чтение задач продолжает работать без optional scopes.

Официальная инструкция Bitrix24: [Create webhooks and apps in Bitrix24](https://helpdesk.bitrix24.com/open/21133100/).
Для изменения существующего webhook откройте **Приложения → Ресурсы разработчика →
Интеграции**, затем меню (≡) нужной записи. Если администратор редактирует webhook другого
пользователя, Bitrix24 меняет владельца на администратора и сбрасывает секрет; после этого
запустите установщик повторно и введите новый URL.

## 2. Рекомендуемая установка одной командой

Требуется Iva `0.4.0` или новее. Подключитесь к серверу по SSH под тем Unix-пользователем,
которому принадлежит установка Iva, и выполните:

```bash
curl -fsSL https://raw.githubusercontent.com/mamysh/iva-bitrix24/main/install.sh | bash
```

Репозиторий можно подключить как собственный Marketplace Iva и установить плагин по имени:

```bash
iva plugin marketplace add mamysh/iva-bitrix24
iva plugin add bitrix24-read@iva-bitrix24
```

Этот путь использует штатные рельсы Iva, но оставляет настройку webhook пользователю; для
первой установки рекомендуется мастер выше. Marketplace-запись отслеживает ветку `stable`,
поэтому установленный источник совместим с последующим `iva plugin update` и кнопочным
обновлением из Telegram, но не предлагает release candidates из `main`.

Для отправки файлов настоящими вложениями установите и включите отдельный плагин
`iva-file-delivery`. Для просмотра PDF-страниц на сервере нужен `pdftoppm` (пакет
`poppler-utils`), а для презентаций, Word и Excel при полном визуальном разборе —
`libreoffice`. LibreOffice также нужен для текстового разбора PPT/PPTX.
Без этих программ файлы по-прежнему можно скачать и отправить;
визуальный разбор соответствующего формата сообщит об ограничении.
Мастер проверяет LibreOffice и, если он отсутствует, на Ubuntu/Debian спрашивает,
установить ли `libreoffice-impress-nogui`, `libreoffice-writer-nogui` и
`libreoffice-calc-nogui` без графического интерфейса. Только после ответа «да» он
вызывает `sudo apt-get install`; при отказе или ошибке продолжает настройку плагина.
На VPS с менее чем 1,5 ГБ RAM мастер предупредит о возможной медленной обработке
крупных презентаций.

Мастер использует `/dev/tty`, поэтому остаётся интерактивным внутри pipe. Он:

1. добавляет `mamysh/iva-bitrix24/plugin@stable` через штатный `iva plugin add` без trust;
2. объясняет, какой входящий webhook создать;
3. принимает URL скрыто, проверяет `profile` и `tasks.task.getFields`;
4. атомарно сохраняет `data/custom/plugins/bitrix24-read.env` с правами `0600`,
   включая абсолютный путь к `vault/attachments/`, определённый из установки Iva;
5. после явного подтверждения выполняет `iva plugin trust bitrix24-read` и `iva doctor`;
6. предлагает вернуться в Telegram и написать Иве: «Проверь подключение и покажи возможности
   Bitrix24».

При проверке и после обновления из Telegram Ива сообщает фактические имя сервера,
пользователя и проверенный путь установки. Для Ubuntu/Debian с доступными пакетами
она показывает команду установки LibreOffice: подключитесь к указанному серверу по SSH
и выполните её. Затем попросите Иву проверить статус обновления: статус заново проверит
наличие LibreOffice. Повторно вводить webhook ради установки пакета не требуется.
Фоновое обновление плагина системные пакеты не устанавливает. Если обновление идёт со
старой версии, первый экран подтверждения может ещё не содержать эту инструкцию; она
появится в статусе после обновления. Если путь установки не удалось подтвердить, Ива
не показывает команду и предлагает обратиться к администратору сервера.

Не запускайте мастер от `root`: он должен работать с теми же файлами и systemd user units,
что и Iva.

## 3. Прозрачный ручной fallback

Если bootstrap недоступен, установите подпапку плагина напрямую без клонирования репозитория:

```bash
iva plugin add mamysh/iva-bitrix24/plugin@stable
```

После добавления ожидается состояние `enabled · untrusted`. Не включайте trust до создания
env-файла. Из корня установки Iva создайте пустой файл с закрытыми правами:

```bash
install -m 600 /dev/null data/custom/plugins/bitrix24-read.env
${EDITOR:-vi} data/custom/plugins/bitrix24-read.env
```

Добавьте строки конфигурации:

```dotenv
BITRIX24_WEBHOOK_BASE_URL=https://example.bitrix24.com/rest/USER_ID/WEBHOOK_SECRET
BITRIX24_ATTACHMENTS_ROOT=/absolute/path/to/iva/vault/attachments
BITRIX24_SETTINGS_DEFAULTS=restricted
```

Замените пример внутри редактора и сохраните файл. Не используйте `echo` и не передавайте
webhook аргументом команды.

Вторая строка должна указывать именно на каталог `attachments` внутри используемого Iva
vault. Без неё новые инструменты скачивания сообщат об отсутствующей настройке. Если vault
задан через `ASSISTANT_VAULT_DIR`, используйте это расположение.

Проверьте права:

```bash
stat -c '%a %n' data/custom/plugins/bitrix24-read.env
```

Ожидаемые права — `600`.

## 4. Разрешите запуск при ручной установке

Все команды жизненного цикла выполняйте под тем Unix-пользователем, которому принадлежит
установка Iva:

```bash
iva plugin trust bitrix24-read
iva plugin list
iva doctor
```

На Linux Iva запускает stdio MCP-сервер через собственный loopback proxy и systemd user
service. На системе без systemd состояние trust может сохраниться без автоматического запуска
процесса.

## 5. Проведите первый тест

В новом диалоге попросите Iva проверить подключение и показать возможности. Первый вызов
использует `bitrix24_connection_check`, второй — `bitrix24_capabilities`, который не читает
рабочие объекты. Затем запросите небольшую страницу собственных задач; начните со scope
`mine`, чтобы проверить границы доступа пользователя webhook.

Для проверки дополнительных блоков используйте одну тестовую доступную задачу: попросите
показать её обсуждение, файлы, чек-лист и связи; отдельно найдите один проект, сотрудника и
подразделение. Плагин не сохраняет эти ответы, но они проходят через модель и историю диалога,
поэтому выбирайте данные, которые допустимо показывать личной Iva.

Для локальной диагностики разработчика предусмотрен безопасный smoke-test:

```bash
npm run smoke:live -- /absolute/path/to/secrets.env
```

Файл должен иметь права `0600` и содержать `BITRIX24_WEBHOOK_BASE_URL`. Smoke-test вызывает
только allowlisted read-only методы и выводит проверки формы ответа, а не значения профиля и
задач.

## 6. Обновление из Telegram

Этот сценарий работает, только если экземпляр установлен из GitHub, например командой из
раздела 2 или `iva plugin add mamysh/iva-bitrix24/plugin@stable`. Напишите Иве в личном чате:
«Проверь обновление Bitrix24-плагина».

Ива покажет текущую и кандидатную SemVer-версии и статус GitHub Actions. Если CI успешен,
появится нативный запрос подтверждения с кнопками. Проверьте переход между версиями и нажмите
кнопку согласия; копировать фразу или SHA не нужно. SHA проверяется внутри updater и доступен
для технической диагностики. Отказ откладывает обновление.

Фоновый worker вызывает штатный `iva plugin update bitrix24-read`, сверяет установленный SHA
и запускает `iva doctor`. Через минуту спросите Иву о статусе. При провале диагностики worker
пытается вернуть предыдущую версию; после такого отката не запускайте повтор без разбора причины.
Push в GitHub сам по себе production не меняет.

Если apply вернул ошибку, не просите Иву выполнять `iva plugin update`, `systemctl` или restart
через shell. Попросите только показать status. Ручное восстановление выполняется владельцем в
терминале: updater, запущенный как дочерний процесс самой Iva, может быть убит вместе с ней во
время штатной пересборки. `stalled` означает, что job не вышла из очереди за две минуты;
`superseded` — что после записанной job установленная версия уже изменилась другим путём.
Штатный restart Iva может сопровождаться её общим сообщением об оборванном предыдущем ходе;
ориентируйтесь на отдельный статус update-job.

Экземпляр, установленный из локальной папки, ответит `local_source`. Его необходимо один раз
контролируемо переустановить из GitHub с сохранением
`data/custom/plugins/bitrix24-read.env`. Не редактируйте `plugins.json` вручную.

## 7. Обновление при разработке и восстановление

После обновления исходников пересоберите и проверьте проект, затем синхронизируйте плагин:

```bash
npm ci
npm run check
iva plugin update bitrix24-read
iva doctor
```

`iva plugin sync` не получает новую версию: он восстанавливает согласованность с уже
записанным состоянием. Используйте его только по рекомендации `iva doctor`.

Проверяйте release notes Iva перед обновлением. Заявленная матрица совместимости относится
только к версиям, указанным в README.

## 8. Отключение, удаление и ротация

Остановить доверенный процесс:

```bash
iva plugin untrust bitrix24-read
```

Скрыть capability из Iva:

```bash
iva plugin disable bitrix24-read
```

При удалении отдельно решите судьбу `data/custom/plugins/bitrix24-read.env` и данных из
`data/plugin-data/bitrix24-read/`: они могут переживать переустановку по политике Iva.

Если webhook попал в лог, чат, shell history или git, немедленно отзовите его в Bitrix24,
создайте новый и замените значение через редактор. Не ограничивайтесь удалением строки из
файла или commit.

## Troubleshooting

- `enabled · untrusted`: env ещё не настроен либо процесс не получил trust.
- `CONFIGURATION_ERROR`: проверьте наличие переменной, HTTPS, отсутствие query/fragment и
  канонический путь `/rest/USER_ID/WEBHOOK_SECRET`.
- `NO_AUTH_FOUND`: webhook отозван, неверен или недоступен пользователю.
- `INSUFFICIENT_SCOPE`/`insufficient_scope`: посмотрите `requiredScope` или вызовите
  `bitrix24_capabilities`, затем через **Приложения → Ресурсы разработчика → Интеграции**
  добавьте только названное право. После возможной смены секрета снова запустите installer.
- `ACCESS_DENIED`: scope может быть правильным, но у пользователя webhook нет доступа к
  конкретной задаче, чату, файлу, проекту или другому объекту; исправьте права самого
  пользователя, а не добавляйте все scope подряд.
- Пустой список при `scope=mine`: проверьте, назначены ли задачи пользователю webhook.
- Ошибки после обновления Iva: выполните `iva plugin sync`, затем `iva doctor`.

При публикации issue используйте только коды ошибок и синтетические примеры. Не прикладывайте
env-файл, полный URL запроса или сырой REST-ответ.

## Действия с задачами (0.7.0)

Для записи используется тот же webhook. Требуются `task` и `user_brief` (либо более широкий
user scope), для современного чата и файла — `im`, для смены ответственного — `department`,
для проекта — `sonet_group`. Scopes не заменяют объектные права сотрудника.

Ива передаёт private `PLUGIN_DATA`; без него запись закрыта с `WRITES_NOT_CONFIGURED`.
Для загрузки установщик сохраняет `BITRIX24_ATTACHMENTS_ROOT`. В версии
0.7.0 старое подключение без этого поля восстанавливает каталог из проверенного
CLI Ивы и настройки её vault при запуске MCP, без перезаписи webhook. Если проверка
установки не прошла, требуется повторный запуск установщика. Инструмент принимает путь
относительно этого каталога. Без чата задачи загрузка недоступна. Отдельный scope `disk`
для `im.v2.File.upload` не нужен; он остаётся нужен для чтения файлов через Drive APIs.

Перед использованием новой версии проверьте сценарии из [TASK_WRITES](TASK_WRITES.md)
на тестовой задаче. Не считайте синтетические тесты подтверждением live-совместимости.
После аварийного завершения внутри действия может остаться `PLUGIN_DATA/task-writes/lock`.
Администратор сначала останавливает MCP-процесс, проверяет сохранённую квитанцию и фактическую
задачу, затем удаляет только каталог lock и запускает процесс. Не удалять квитанции для
повторного выполнения неизвестного результата.

## Переход с RC на stable

Стабильный выпуск 0.7.0 включает действия с задачами. Установщик и Marketplace используют
`@stable`. Если плагин уже установлен из `@stable`, достаточно обычного обновления из чата.

Если установлен точный RC-тег, например `@v0.7.0-rc.7`, он закрепляет предварительный выпуск и не перейдёт
на 0.7.0 автоматически. Для дальнейших стабильных обновлений смените источник на `@stable`.

Перед сменой источника сохраните резервные копии env и private plugin-data. В них секрет
подключения и квитанции действий: не отправляйте их в чат или репозиторий.
Штатное remove сохраняет данные плагина. На сервере под пользователем Ивы выполните:

```bash
iva plugin remove bitrix24-read
iva plugin add mamysh/iva-bitrix24/plugin@stable
iva plugin trust bitrix24-read
iva doctor
```

Проверьте, что env-файл сохранён, затем попросите Иву проверить подключение.
Тот же процесс переводит установку из `@main` на стабильный канал.
Не редактируйте `plugins.json` вручную и не удаляйте квитанции ради повторения неизвестного результата.

Чтобы закрепить именно 0.7.0, используйте `@v0.7.0` вместо `@stable`.
Точный тег фиксирует выпуск и не получает следующие версии автоматически.

Для записи нужен доступ к пользователям; для файлов и обсуждения — к чату, для сведений о
подразделениях — к подразделениям, для проекта — к рабочим группам. После обновления с 0.5.4
проверьте нужные scopes существующего webhook по разделу выше. Предоставлять все права не нужно.

Владелец подтвердил создание и закрытие задачи в боевой работе на актуальной Иве Шимы.
Другие операции имеют автоматические проверки; отдельная live-проверка не заявляется.
Точный контракт и ограничение передачи подтверждения через модель — в [TASK_WRITES](TASK_WRITES.md).


## Возможности версии 0.7.0

Версия добавляет правку карточки и чек-листа, составные действия с одним подтверждением
и оформление ответов. Также доступны канбан, удаление выбранного файла или сообщения
из чата задачи и исправление остановки общего апрува на пунктах чек-листа. Сохраните резервную копию env и plugin-data;
квитанции нельзя удалять для повтора действий. Чтобы закрепить этот выпуск, выполните под пользователем Ивы:

```bash
iva plugin remove bitrix24-read
iva plugin add mamysh/iva-bitrix24/plugin@v0.7.0
iva plugin trust bitrix24-read
iva doctor
```

Env и квитанции сохраняются штатным remove. Тег закрепляет эту версию; для дальнейшего
перехода повторите процедуру с новым тегом или `@stable`. После обновления проверьте
подключение и новый сценарий на тестовой задаче. В личном Telegram-чате с Telegram-poll
используется rich-превью с кнопками через существующую Иву; её ядро не меняется.
При webhook-only, в группах и других каналах используйте presentation=native: ask_question.

В 0.7.0 почта в подтверждении берётся из аккаунта при scope user_basic/user.
Должность берётся из WORK_POSITION (доступно и при user_brief); для названий
подразделений используется уже выданное право department. Без него подразделение
помечается недоступным, действие остаётся доступно. Пустая должность помечается не указанной.
Без права на почту или при пустой почте плагин показывает имя, ID и пометку «почта недоступна».
Черновик RC5 или более ранней версии нужно подготовить и подтвердить заново;
сохранённые результаты операций остаются доступными. Rich-подтверждение требует
rich-replies и Telegram-poll. Если rich-кнопки не появились, попросите новое нативное
подтверждение; обычное «да» не разрешает запись. После успешного выбора старые
кнопки могут оставаться в чате: повтор не выполняет операцию заново.


## Меню настроек плагина

Доступно в предварительном выпуске 0.7.1-rc.1; stable 0.7.0 меню не содержит.
После установки поддерживающей версии попросите Иву «Покажи настройки Битрикс» в личном чате.
Главная карточка проверяет profile и tasks.task.getFields, без чтения задач; раздел возможностей
читает scope. Каждый тап запускает ход Ивы и возвращает новый экран. Встроенное `/menu` не меняется.

Настройки сохраняются в private `PLUGIN_DATA/settings.json` (schema1, revision, mode,
uploads, deletions, people, email), файл 0600 и каталоги 0700. Стандартное обновление сохраняет
PLUGIN_DATA. Данные не хранятся в папке поставки плагина. Изменение сначала создаёт предложение
с TTL 10 минут; подтверждение привязано к revision, порталу/пользователю webhook и случайному
одноразовому ответу. Более новое предложение заменяет прежнее. Общая task-writes/lock не даёт
переключить настройки посреди выполнения пакета. После сохранения pending-превью отменяется;
завершённые квитанции сохраняются.

| Режим | Результат |
| --- | --- |
| Только чтение | Все изменения на портале закрыты, включая создание, комментарии и стадии. Чтение и скачивание доступных файлов остаются. |
| Запись с подтверждением | Разрешены поддерживаемые действия с прежним полным превью/подтверждением, если разрешены порталом. |
| Загрузка / удаление | Отдельные разрешения внутри режима записи; загрузка учитывается и при создании/пакете. Удаление ограничено поддерживаемыми сообщениями и файлами чата, удаление задач не добавлено. |
| Только ID | Имена и профильные сведения исключены из структурированных ответов/превью; поиск сотрудника по имени закрыт. |
| ID и имена | Имя доступно, email, должность и подразделения профиля скрыты. |
| Рабочий профиль | Имя, должность и подразделения доступны; email включается отдельно и зависит от user_basic/user scope. |

Телефоны, адреса и фотографии профилей не запрашиваются. Свободные тексты, history values,
имена файлов и содержимое документов могут содержать персональные данные: настройка не
обезличивает их и не удаляет уже полученные данные из переписки/vault Ивы.

Свежий запуск установщика 0.7.1-rc.1 без прежнего env записывает `BITRIX24_SETTINGS_DEFAULTS=restricted`:
чтение, ID, без загрузки/удаления/email. При перенастройке прежнего env без маркера установщик
записывает `legacy`, сохраняя прежнее поведение (подтверждаемая запись, загрузка/удаление,
рабочий профиль/email по доступным правам). Повторный запуск сохраняет restricted-маркер.
Ручная новая конфигурация должна явно добавить `BITRIX24_SETTINGS_DEFAULTS=restricted` в
закрытый env-файл. Отсутствующий маркер при настроенном webhook считается прежней установкой;
угадать её возраст по квитанциям или имени ветки плагин не пытается. Сохранённая settings.json
имеет приоритет над маркером. Режимы не добавляют прав webhook; их меняют на портале.

Если private data недоступны, чтение выдаёт минимум полей, запись/изменение настроек закрыты.
Повреждённый settings.json вызывает SETTINGS_INVALID: штатные read/write tools закрываются
до выборки данных. Не удаляйте файл ради восстановления старых разрешений: проверьте его
в терминале или восстановите проверенную копию. WRITE_BUSY означает выполняемое действие
либо старую блокировку после сбоя; проверьте квитанцию и операторский порядок восстановления.
SETTINGS_CHANGED/SETTINGS_OFFER_INVALID требуют открыть новое меню и повторить выбор.

Webhook URL не передаётся в чат и не выводится в карточке; менять секрет по-прежнему нужно
через терминальный установщик. Обновление самого плагина — отдельная процедура, его
подтверждение не связано с режимом действий на портале. Для других каналов skill использует
native ask_question после выбора, а не пытается восстановить Telegram-кнопки.


## Установить меню из предварительного выпуска

Для новой установки выберите точный RC под пользователем Ивы:

```bash
iva plugin add mamysh/iva-bitrix24/plugin@v0.7.1-rc.1
iva plugin trust bitrix24-read
iva doctor
```

Для уже установленного плагина сначала сохраните резервную копию env и plugin-data,
затем смените источник штатными командами:

```bash
iva plugin remove bitrix24-read
iva plugin add mamysh/iva-bitrix24/plugin@v0.7.1-rc.1
iva plugin trust bitrix24-read
iva doctor
```

Штатный remove сохраняет env и квитанции. Не редактируйте registry вручную.
Тег закрепляет RC; `@stable` остаётся на 0.7.0. Обновление с 0.7.0 сохраняет прежнюю
политику до выбора в меню. Pending-превью schema4 нужно подготовить заново: RC использует
schema5 с revision настроек. Завершённые квитанции остаются доступны. После установки
попросите «Покажи настройки Битрикс»; живые нажатия и изменение настроек этого RC
автоматическими проверками не подтверждены.
